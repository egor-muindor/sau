# Архитектура

Устройство `sau` — утилиты для загрузки переводов на smotret-anime.online.

Протокол взаимодействия с сайтом описан отдельно в [protocol.md](protocol.md)
и здесь не дублируется.

## 1. Задача

Переводчик регулярно выкладывает озвучку выходящего онгоинга: одна серия примерно
раз в неделю, видеофайл целиком, через веб-форму сайта. Форма требует ручных шагов
на каждую серию, а заливка большого файла занимает долгое время и рвётся.

Нужна CLI-утилита на Go, которая делает это одной командой, переживает обрыв связи
и не требует присутствия человека у экрана.

## 2. Область работ

Входит:

- вход на сайт и удержание сессии;
- чанковая заливка видео с докачкой, параллелизмом и переключением между зеркалами;
- заливка субтитров (тот же протокол, другой список расширений);
- заполнение и отправка формы перевода;
- предупреждение о возможном дубле (именно предупреждение, не запрет публикации);
- журнал выполненных публикаций и статистика по нему;
- работа на macOS, Linux и Windows.

Не входит:

- headless-браузер в поставке (Playwright использовался только для разведки);
- слежение за папкой и автоматический запуск по появлению файла;
- редактирование и удаление уже опубликованных переводов;
- работа с несколькими аккаунтами одновременно.

## 3. Архитектура

Слоистая схема, зависимости строго вниз.

```
cmd/sau/                 точка входа: сигналы, код возврата
internal/
  translation/           домен: Draft, типы перевода и серии, валидация
  site/                  транспорт №1: Yii-страницы, CSRF, форма, read-only API
  fineup/                транспорт №2: чанковый протокол Fine Uploader
  publish/               сценарий: логин → форма → заливка → поле → отправка
  statefile/             атомарные JSON-файлы состояния
  session/               cookie jar с сохранением сроков жизни
  secrets/               источники пароля, непечатаемый тип Secret
  httplog/               единственная точка логирования HTTP, с редакцией
  config/                слияние флагов, env, файлов; платформенные пути
  progress/              отображение прогресса
  fsx/                   приватная запись файлов и проверка прав
  history/               журнал выполненных публикаций и агрегаты по нему
  cli/                   разбор аргументов, сборка зависимостей, вывод
```

Направление зависимостей:

- `cli` → всё;
- `publish` → `translation`, типы `site`, типы `fineup`;
- `site` → `translation`, тип `secrets.Secret`;
- `statefile`, `session`, `secrets` → `fsx` (приватная запись и проверка прав);
- `fineup`, `httplog`, `translation`, `fsx` — листья.

### Границы

`fineup` не знает ни про аниме, ни про Yii. Его вход — «залей этот файл на эти хосты»,
выход — результат и поток событий. Это самостоятельный клиент Fine Uploader,
переносимый в другой проект без изменений.

`site` знает про HTML-страницы Yii и умеет закодировать доменный `Draft` в поля формы.
Разбор HTML вынесен в чистые функции над `io.Reader`, чтобы тестироваться на фикстурах.

`publish` — единственный, кто знает последовательность шагов и умеет читать и писать
состояние. Ни `site`, ни `fineup` о persistence не подозревают: файлы состояния, cookie
и конфиг собираются в `cli`.

Upload-серверы нигде не сохраняются. Они добываются парсингом свежей страницы формы
перед каждой заливкой, потому что меняются со временем.

## 4. Ключевые типы

```go
// translation — домен
type Draft struct {
    SeriesID      int
    EpisodeNumber string           // строка: допускает "5.5"
    EpisodeType   EpisodeType      // tv|ova|ona|movie|special|tv_special|preview
    Type          TranslationType  // raw|subJa|subEn|voiceEn|subUk|voiceUk|subRu|voiceRu
    Authors       string
    AddedByAuthor bool
    VideoPath     string
    SubPath       string
}
type Channel int // All=0, CDN=2, RU=3
```

```go
// site
type UploaderConfig struct {
    ServerID   int
    ServerURL  string   // базовый хост
    ServerURLs []string // пул хостов для чанков
    AllowedExt []string
}
type CreateForm struct { CSRF string; Video, Sub UploaderConfig }

func (c *Client) Login(ctx, user string, pass secrets.Secret) error
func (c *Client) CreateForm(ctx, seriesID int, ch translation.Channel) (CreateForm, error)
func (c *Client) Submit(ctx, f CreateForm, d translation.Draft, up UploadedFields) (SubmitResult, error)
```

Схема скрытого поля формы изолирована в одном файле `site/uploadfield.go`. Она
воспроизводит захваченную структуру целиком, включая служебные поля браузерного
загрузчика: выяснять опытным путём, какие из них сервер игнорирует, дороже,
чем повторить всё. Уточнение схемы затрагивает только этот файл и его golden-тест.

```go
// fineup
type Spec struct {
    Path     string
    Base     string   // нормализованный базовый URL + /upload.php
    Pool     []string // хосты для чанков, всегда свежие
    UUID     string   // пустой → сгенерировать; при докачке — из состояния
    PartSize int64    // 5_000_000
    Done     []int    // уже залитые индексы чанков
    MaxConns int      // 5
}
type Result struct { UUID, Name string; Size int64; Parts int; Endpoint string }

func (u *Uploader) Upload(ctx, s Spec, on func(Event)) (Result, error)
func (u *Uploader) Delete(ctx, endpoint, uuid string) error
```

Интерфейсов ровно пять, все объявлены на стороне потребителя: `Site`, `Uploader`,
`StateStore`, `Reporter` в `publish` и `secrets.Source`. Каждый — либо шов для теста,
либо точка подмены реализации. Внутри `site` и `fineup` интерфейсов нет: там всё
проверяется поднятием тестового HTTP-сервера.

## 5. Конфигурация и секреты

Приоритет источников: флаги → переменные `SAU_*` → проектный `./.sau.toml` →
пользовательский `config.toml` → умолчания.

Проектный файл кладётся в папку онгоинга и хранит постоянные для тайтла значения:
идентификатор сериала, тип серии, тип перевода, авторов, канал.

**Upload-серверы запрещено хранить** в конфиге и состоянии как источник истины;
валидация конфига отвергает такие ключи, если они появятся.

### Пароль

Нужен только для входа. Цепочка источников: `SAU_PASSWORD` → файл из
`SAU_PASSWORD_FILE` → системное хранилище → интерактивный ввод.

Файловый источник следует конвенции `_FILE` и покрывает docker secrets и
`LoadCredential=` в systemd — это и есть ответ на headless-окружение.

Тип `Secret` не печатается ни через форматирование, ни в JSON, ни в структурном логе —
везде подставляется заглушка. Единственный метод доступа к значению вызывается
в одном месте: при кодировании формы логина.

Пароль не попадает в конфиг, состояние, cookie-файл и логи **по конструкции типа**,
а не по дисциплине вызывающего кода. Хранилища паролей открытым текстом нет
и не планируется.

### Сессия

Сайт выдаёт долгоживущую cookie входа примерно на месяц. Поэтому пароль требуется
в среднем раз в месяц, а не при каждом запуске. Cookie сохраняются с сохранением
сроков жизни, файл пишется приватно.

Смена пароля инвалидирует сессию — это обычная ошибка «не авторизован»,
обрабатываемая повторным входом, отдельной ветки не требует.

### Логирование

Весь HTTP обоих транспортов проходит через один транспорт-логгер с редактором.
Заголовки авторизации и cookie, поля формы логина и токен CSRF заменяются заглушкой.
Тела логируются только для форм, с ограничением по размеру; бинарные и multipart —
только размером.

Правило: то, что не прошло через редактор, в логгер не попадает вообще. Точечных
исключений по коду нет. На это есть регрессионный тест — см. раздел о тестировании.

### Зеркала сайта

Сайт доступен через несколько равнозначных доменов; на момент написания отвечают
`smotret-anime.online`, `smotret-anime.org`, `smotret-anime.ru`, `anime-365.ru`
и `anime365.ru`. Это важно при блокировках у провайдера.

Адрес задаётся настройкой, список запасных — тоже. При недоступности текущего
зеркала программа пробует следующее.

**Важная тонкость: сессия привязана к домену.** Cookie входа выдаётся на конкретный
домен, поэтому вход, полученный на одном зеркале, **не действует на другом**.
Отсюда два следствия:

- хранилище сессий ведётся **по зеркалам**, а не одной записью; переключение
  на другое зеркало означает вход заново, если для него нет живой сессии;
- переключение зеркала в середине заливки бессмысленно и не делается: зеркала
  нужны для страниц сайта, а чанки уходят на отдельные upload-серверы, которые
  от домена сайта не зависят.

Ссылки, которые сайт возвращает в API, могут указывать на другой домен, чем тот,
через который шла работа. Это нормально, приводить их к одному виду не требуется.

## 6. CLI

Стандартная библиотека `flag` плюс небольшой диспетчер команд. Команд пять, вложенности
нет, автодополнение не требуется — внешняя библиотека не окупается и тянет за собой
лишнее.

```
sau login    [--user U] [--save-password] [--check]
sau upload   <video> [--sub f.ass] --episode N [--series ID]
             [--episode-type tv] [--type voiceRu] [--authors "..."] [--by-author]
             [--channel cdn|all|ru] [--dry-run] [--no-submit] [--fresh]
             [--concurrency 5] [--json] [-v]
sau status                незавершённые заливки
sau abort    <video>      удалить залитое с сервера и стереть состояние
sau resolve  <video> --submitted | --resend
                          разрешить неясный исход отправки без диалога
sau series   <id>         справка по тайтлу из read-only API
sau stats    [--series ID] [--since DATE] [--json]
                          статистика по журналу публикаций
```

Флаг `--debug` — уровень подробности выше `-v`: полный след HTTP-обмена
(всегда через редактор), тайминги каждого чанка, выбор хостов балансировщиком
и решения политики докачки. След пишется в файл рядом с журналом, чтобы его
можно было приложить к разбору сбоя, не переснимая заливку.

Канал по умолчанию — **CDN** (решение пользователя).

`--dry-run` выполняет всё, что не имеет побочных эффектов: проверяет сессию, забирает
свежую страницу формы, валидирует файл и черновик, предупреждает о существующем
переводе той же серии, печатает план заливки и вердикт по докачке. Чанки не шлёт,
форму не отправляет.

`--no-submit` заливает файл и печатает готовое значение скрытого поля, но форму
не отправляет. Это же — штатный инструмент для закрытия оставшегося вопроса
по схеме поля.

Коды возврата: `0` успех, `1` общая ошибка, `2` ошибка вызова, `3` авторизация,
`4` сайт отверг данные, `5` заливка не удалась (состояние сохранено, докачка возможна),
`6` исход отправки неизвестен и требует решения человека, `130` прервано.

## 7. Модель ошибок

Типизированные ошибки заводятся только там, где по ним ветвится логика; общего
перечисления видов ошибок нет.

| Ситуация | Реакция |
|---|---|
| сеть, таймаут, 5xx, 408, 429 | повтор с нарастающей паузой |
| чанк отвергнут | до 4 попыток: другой хост, если в пуле больше одного; иначе тот же хост с нарастающей паузой |
| пул исчерпан | один раз: свежая страница формы и продолжение с новым пулом |
| финализация не удалась | одна попытка с полным перезаливом того же идентификатора |
| не авторизован | один повторный вход и повтор запроса |
| сайт отверг форму | без повтора: показать сообщения сайта, код 4 |
| отмена пользователем | без повтора: состояние уже на диске, код 130 |

**Отправка формы не повторяется автоматически** — она не идемпотентна, и повтор
рискует создать дубль публикации.

Различение по ответу: редирект — успех, страница с блоком ошибок — отказ,
страница логина — протухшая сессия. Ошибки транспорта **не сваливаются в одну кучу**,
а делятся на два класса — см. таблицу ниже. Успешный редирект подтверждён
живой отправкой.

### Исход отправки формы

Публикация **не появляется в read-only API сразу** после успешной отправки: есть
задержка индексации в несколько минут. Проверено на реальной отправке — сразу после
неё полного обхода переводов тайтла не хватило, чтобы найти новую запись; спустя
несколько минут она появилась. Транскодирование при этом не требуется.

Нескольких минут достаточно, чтобы правило «спросить API» дало ложный ответ.

Поэтому API не участвует в решении о повторе. Исход определяется только ответом
на саму отправку и различается на четыре случая:

| Исход | Признак | Действие |
|---|---|---|
| успех | редирект | состояние закрывается немедленно, API не опрашивается |
| отвергнуто | страница с блоком ошибок | показать причины, состояние сохранить, код 4; повтор безопасен — сайт ничего не создал |
| точно не отправлено | запрос не дошёл до сервера: отказ соединения, ошибка имени, сертификат | до трёх повторов, затем код 5 |
| **неизвестно** | всё остальное: таймаут, обрыв после отправки тела | особая фаза, **автоповтор запрещён навсегда**, код 6 |

Неизвестный исход разрешает только человек. Программа сохраняет слепок того, что
отправлялось, и при следующем запуске показывает его и спрашивает, виден ли перевод
на сайте. Для окружений без консоли есть отдельная команда с явными флагами.

Подсказка прямо предупреждает: отсутствие записи в API не доказывает, что отправки
не было. Без этого правила самый частый сбойный сценарий — отправка прошла, программа
упала сразу после — приводил бы к дублю публикации.

Опрос API остаётся только как предупреждение в `--dry-run` и справочной команде,
где ложноотрицательный ответ безвреден.

### Проверка дубля

Фильтра по номеру серии в API нет, поэтому проверка трёхшаговая: получить список
эпизодов тайтла и найти нужный по номеру, запросить переводы тайтла нужного типа,
отобрать записи с этим эпизодом и сверить авторов.

Сверка авторов обязательна: у одной серии популярного онгоинга бывает 7–9 озвучек
от разных команд, и совпадение только по эпизоду и типу означало бы чужую работу.

**Сверка обязана нормализовать строку авторов.** Сайт переписывает её при сохранении:
отправленная запятая между участниками возвращается из API амперсандом. Дословное
сравнение не совпадёт никогда. Нормализация приводит к общему виду разделители,
регистр и пробелы.

API молча игнорирует неизвестные параметры и сегменты пути, возвращая правдоподобные,
но неверные данные. Поэтому клиент обязан перепроверять выдачу у себя, а не полагаться
на то, что фильтр применился.

## 8. Докачка

Состояние хранится по одному файлу на заливаемый файл, запись атомарная,
после каждого успешного чанка.

```go
type UploadState struct {
    UUID       string
    PartSize   int64
    TotalParts int
    Done       []int
    ServerID   int                  // где лежат чанки — только для сравнения
    Channel    translation.Channel  // канал, в котором заливали
    Result     *fineup.Result
}
```

### Фазы

`uploading` → `uploaded` → `submitted`. Успешная отправка закрывает состояние
и удаляет файл.

Отдельная фаза — **`submit_unknown`**: отправка ушла, но ответ не получен.
Вместе с ней сохраняется время отправки и слепок отправленного — все поля формы,
кроме токена и содержимого скрытого поля. Без слепка программе нечего показать
человеку, когда она спросит, появился ли перевод на сайте.

Из этой фазы нет автоматического выхода. Разрешает её только человек: диалогом
при следующем запуске либо отдельной командой с явным флагом, если консоли нет.
Флаг «отправить заново» возвращает состояние на обычный путь — свежая страница,
проверка сервера и канала, отправка.

Идентификатор заливки принадлежит физическому серверу, а хосты — лишь маршруты к нему.
Поэтому хосты не сохраняются никогда, а сохраняется пара «сервер + канал».

**Докачка разрешена, только если совпали и сервер, и канал.** Канал входит в условие
потому, что идентификатор сервера одинаков для разных каналов, а множества хостов
при этом не пересекаются; считать их общим хранилищем без проверки нельзя.

| Ситуация | Действие |
|---|---|
| состояния нет | новая заливка |
| файл изменился | предупредить и начать заново |
| сервер и канал совпали | докачка при любой смене хостов |
| канал не совпал | **отказ с кодом 2** и подсказкой: продолжить в прежнем канале или начать заново явным флагом |
| сервер сменился, файл не собран | начать заново с явным сообщением |
| сервер сменился, файл собран | перезалить |
| финализация не удалась после докачки | одна попытка с полным перезаливом |

Отказ при смене канала, а не молчаливый перезапуск, — потому что канал живёт
в файле конфигурации и меняется почти всегда случайно, а перезапуск без спроса
выбрасывает часы уже залитого. Cookie канала выставляется всегда явно, включая
значение по умолчанию, чтобы сохранённый канал был фактом, а не умолчанием.

Токен CSRF для отправки формы берётся из запроса, сделанного **после** заливки:
он меняется на каждой загрузке страницы.

Ограничение протокола: узнать у сервера, какие чанки у него уже есть, нельзя,
а срок жизни недозалитого неизвестен. Отсюда одна автоматическая попытка
с полным перезаливом.

## 9. Конкурентность

Файл открывается один раз и читается позиционно, что безопасно из нескольких горутин.
Чанки заливаются группой с ограничением в пять одновременных; первая фатальная ошибка
отменяет остальные.

Пока идёт заливка, отдельная горутина каждые 15 секунд пингует сервер, иначе он
подчищает недозалитое. Она гарантированно завершается до возврата из заливки —
на это есть проверка отсутствия утечек горутин.

Прогресс считается атомарным счётчиком; отрисовка троттлится отдельной горутиной,
чтобы вывод не тормозил заливку.

Выбор хоста для чанка: по порядковому номеру, пока хватает хостов, затем самый быстрый
по замерам, затем случайный из исправных; если исправных не осталось — отметки
сбрасываются.

**При пуле из одного хоста** (канал «РФ») правило исчерпания пула не применяется:
выбор всегда возвращает единственный хост, а исчерпание определяется бюджетом
повторов чанка. Иначе первая же сетевая помеха помечала бы единственный хост сбойным
и мгновенно обрывала заливку.

### Два разных правила склейки адреса

У адреса российского сервера есть завершающий слэш, у остальных нет. Поэтому склейка
разведена на два случая, и это **намеренная асимметрия**:

- **в HTTP-запросах** адрес нормализуется — завершающие слэши срезаются, двойного
  слэша не возникает;
- **в скрытом поле формы** адрес склеивается дословно так же, как это делает
  сценарий сайта, то есть с двойным слэшем для российского канала.

Причина второго правила: именно такую строку отправляет браузер, и сайт её заведомо
принимает. Если он сверяет это значение со своим списком по той же склейке,
нормализованный вариант будет отвергнут — а обнаружится это только после
многочасовой заливки. Дословное воспроизведение дешевле проверки.

Оба правила покрываются тестами на адреса со слэшем и без.

Видео и субтитры заливаются последовательно — субтитры малы, параллелизм не окупается.

## 10. Журнал публикаций

После каждой успешной публикации в журнал добавляется запись. Журнал ведётся
только дописыванием, отдельно от состояния незавершённых заливок: состояние
живёт до конца заливки и удаляется, журнал не удаляется никогда.

Три сущности хранятся **раздельными полями, а не одной строкой** — иначе по ним
нельзя считать агрегаты:

| Сущность | Что хранится |
|---|---|
| тайтл | идентификатор, название, сезон и год |
| серия | номер, идентификатор, тип, полное название из каталога |
| перевод | идентификатор, тип, авторы, адрес страницы, разрешение и качество |

Рядом — измерения самой заливки: размер файла, имя, число чанков, длительность,
средняя скорость, число повторов, какие зеркала использовались, канал раздачи,
идентификатор upload-сервера, время начала и завершения.

Идентификатор перевода берётся из редиректа при успехе — это единственный способ
узнать его сразу, потому что в API запись появляется с задержкой. Адрес страницы
можно получить позже из API и дописать.

Что это даёт помимо истории: видно скорость и стабильность зеркал на реальных
заливках, реальный разброс времени по сериям, частоту повторов и потерянных
чанков, а также пропуски в нумерации серий.

Формат — по строке на запись, чтобы дописывание было атомарным и файл оставался
читаемым глазами. Объём заведомо мал: десятки строк за сезон, поэтому агрегаты
считаются чтением всего файла, без индексов и базы данных.

Отдельная команда выводит сводку с фильтрами по тайтлу и периоду, в виде таблицы
или машиночитаемо.

## 11. Кроссплатформенность

Поддерживаются macOS, Linux и Windows.

| Область | Решение |
|---|---|
| хранилище паролей | системное на всех трёх ОС через общую библиотеку |
| Linux без графической сессии | хранилище пропускается с понятным предупреждением; используется файл или переменная окружения |
| ввод пароля | открытие консоли платформенным способом, чтобы работало при занятом стандартном вводе |
| нет консоли вовсе | понятная ошибка с подсказкой про переменные окружения |
| права файлов | проверка приватности только там, где она осмысленна; на Windows опора на наследуемые права каталога |
| пути | переменные окружения, иначе платформенные каталоги; на Windows состояние в несинхронизируемом каталоге |
| сигналы | набор сигналов разведён по платформам |
| ключ состояния | нормализация пути с учётом регистронезависимости файловых систем |
| прогресс | только возврат каретки и ASCII, без управляющих последовательностей |

Дополнительно учтено: отсутствие корневых сертификатов в минимальных контейнерах,
прокси только из переменных окружения, метка порядка байтов в файле конфига,
и файл, который ещё дописывается кодировщиком — его размер проверяется дважды.

Сборка и тесты обязаны прогоняться на всех трёх системах: тесты, разведённые
по платформам, иначе просто не выполняются.

## 12. Тестирование

Разработка ведётся тестами вперёд (решение пользователя). Порядок — снизу вверх,
каждая ступень самодостаточна и не требует следующей. Все тесты работают без сети.

1. Домен: таблицы разбора и валидации.
2. Чистые функции загрузчика: планирование чанков и выбор хоста, с подставленными
   генератором случайных чисел и часами.
3. Формирование запросов: состав и порядок полей, формат финализации, адрес удаления.
4. Поддельный upload-сервер: пул из нескольких адресов с общим хранилищем и ручками
   для имитации сбоев, задержек, смены пула и очистки. На нём — полный цикл,
   переключение между хостами, отмена, докачка, исчерпание пула, пинг.
5. Разбор страниц сайта на фикстурах, снятых при разведке.
6. Клиент сайта против тестового сервера: вход, форма, отправка, ошибки API.
7. Файлы состояния и cookie: атомарность, приватность, сроки жизни.
8. Секреты: заглушка во всех видах вывода, порядок источников.
9. **Канареечный тест логирования**: прогон входа с приметными значениями пароля,
   имени и cookie; в логе не должно быть ни одного из них. Прогоняется и через
   транспорт, и через клиент целиком, чтобы поймать обход логгера.
10. Сценарий публикации на подставных зависимостях: проверяется последовательность
    вызовов и переходы фаз, включая таблицу докачки.
11. Разбор аргументов и коды возврата на подставном сценарии.
12. Отдельно, вручную: контрактный тест против живого сайта под тегом сборки —
    заливка без отправки формы и удаление. Закрывает вопросы, которые нельзя
    закрыть иначе.

### Три теста, которые важнее остальных

Это места, где ошибка не проявится до реальной заливки, а цена ошибки — испорченная
публикация или её дубль:

- **Точное тело отправки формы** — сверка с захваченным байт в байт: порядок полей,
  два пустых файловых поля, скрытый параметр, канал в двух полях, пустое поле
  субтитров. Сортировка ключей стандартными средствами здесь недопустима: она
  переставит поля и не выразит повтор одного имени.
- **Классификация исхода отправки** — все четыре случая, включая обрыв соединения
  сервером без ответа. Именно здесь решается, будет дубль или нет.
- **Отсутствие обращений к API** на ветках успеха и неизвестного исхода —
  утверждается как факт: подставной API должен получить ноль вызовов.

## 13. Принятые решения

- Язык Go, поставка — одиночный исполняемый файл.
- Полная структура из двенадцати пакетов, несмотря на её размер для утилиты
  такого масштаба; предложение начать с меньшего числа отклонено.
- Разработка тестами вперёд.
- Канал раздачи по умолчанию — CDN.
- Внешние зависимости: разбор HTML, группы горутин, чтение пароля, разбор TOML,
  системное хранилище паролей. Остальное — стандартная библиотека.

## 14. Открытые вопросы

Закрыто разведкой: схема скрытого поля, формат финализации и удаления, отсутствие
поля «запомнить меня», фильтры read-only API, влияние канала на набор серверов,
полный состав полей отправки формы, признак успеха, задержка появления публикации.

Отдельно подтверждено на реальной заливке гигабайтного файла: чанковая схема,
переключение между зеркалами и итоговый успех работают именно так, как описано.

Остаётся:

1. Читает ли сервер служебные поля в скрытом поле формы или ему хватает основных.
2. Разметка ошибок валидации сайта — нужна фикстура для разбора отказа.
   Снимается отправкой заведомо неполной формы.
3. Проверяет ли сайт принадлежность сервера текущей сессии.
4. Срок жизни недозалитого файла без пинга.
5. Требуют ли upload-серверы браузерных заголовков и нет ли перед ними
   антибот-защиты.
6. Как ведёт себя повторная отправка того же чанка.
7. Обработка неанглийских имён файлов. Частично снято: реальный файл назывался
   с пробелами и скобками и прошёл без проблем.
8. Переживает ли cookie входа смену адреса подключения.
9. Меняются ли серверы в пределах одного длительного запуска. Частично снято:
   заливка на 455 запросов прошла без смены пула.
10. Полные правила, по которым сайт переписывает строку авторов. Известен один
    случай: запятая между участниками становится амперсандом. Влияет только
    на нормализацию при проверке дубля.
11. Как выглядят дробные номера серий в каталоге. Влияет на сопоставление серии
    при проверке дубля.

Ни один из оставшихся вопросов не блокирует начало работы: все закрываются
по ходу, на ранних ступенях реализации и контрактном тесте.
